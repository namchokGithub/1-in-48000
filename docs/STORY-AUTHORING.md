# หลักการสร้าง Story Events และ Story Flow

คู่มือนี้ใช้เขียนเนื้อหาใหม่ให้เกม **1 ใน 48,000** โดยยึดโครงเรื่องร่วมที่แตกเป็นกิ่งสั้น ๆ แล้วกลับมารวมกัน ผู้เล่นควรได้พบเหตุการณ์สำคัญของชีวิตมหาวิทยาลัยเหมือนกัน แต่รายละเอียด คนที่พบ และผลของการตัดสินใจต่างกันตามสิ่งที่ทำมาก่อน

กติกาทางเทคนิคที่ใช้จริงอยู่ในส่วน [Story flow contract](GAME-RULES.md#story-flow-contract-step-27) และ Schema ที่ `src/content/v2/schema.ts` หากคู่มือนี้ขัดกับสองแหล่งนั้น ให้ตรวจระบบปัจจุบันก่อนเขียนเนื้อหาเพิ่ม ส่วนก่อนหน้าใน `GAME-RULES.md` บันทึกกติกาเก่าที่เลิกใช้แล้วด้วย

## เริ่มจากช่วงชีวิต ไม่ใช่จากจำนวน Event

1. กำหนดว่าช่วงนี้เริ่มและจบที่ Node ใด รวมถึง `Next Period` ที่เปลี่ยนเวลา
2. เลือกเหตุการณ์หลักที่ผู้เล่นทุกคนควรพบ เรียงให้มีเหตุและผล เช่น พักหลังสอบ → จัดการเงิน → เตรียมเปิดเทอม
3. เพิ่มเหตุการณ์ข้างทางเมื่อสถานะหรือการตัดสินใจก่อนหน้าทำให้ฉากนั้นมีความหมาย เช่น รู้จักมะลิแล้วจึงได้รับข้อความจากมะลิ
4. ให้กิ่งข้างทางกลับเข้าเหตุการณ์หลักที่เหมาะสม ภายในช่วงเดียวกัน เว้นแต่ตั้งใจให้เป็นเส้นเรื่องยาว
5. อ่านทุกเส้นทางตั้งแต่ต้นจนจบช่วง ทั้งเส้นที่ผ่านและไม่ผ่านเงื่อนไข เพื่อดูว่าลำดับเวลาและบทสนทนายังสมเหตุสมผล

จำนวน Event ขึ้นกับจังหวะเรื่อง ไม่ต้องเพิ่มฉากเพียงเพื่อให้ครบจำนวน ผู้เล่นหนึ่งรอบใช้เวลาประมาณ 10–20 นาที จึงควรให้แต่ละฉากมีการตัดสินใจหรือผลทางเรื่องที่ชัดเจน

## เขียน Event และ Choice

- ใช้ภาษาไทยธรรมชาติของนักศึกษาไทยยุคปัจจุบัน มีรายละเอียดชีวิตจริงพอให้เห็นภาพ แต่ไม่อธิบายทุกอย่างแทนผู้เล่น สลับจังหวะตลก อบอุ่น กดดัน และเงียบ ๆ ตามเรื่อง ไม่ใช่ทุกฉากต้องมีดราม่า
- ให้แต่ละ Event มีสถานการณ์หนึ่งเรื่องและคำถามที่ผู้เล่นต้องตัดสินใจ บทพูดก่อนเลือกต้องไม่สรุปผลล่วงหน้า
- แต่ละ Choice ต้องเป็นการกระทำที่ต่างกันจริง ไม่ใช่ข้อความต่างกันแต่ได้ผลเหมือนกันทั้งหมด ทางเลือกที่ไม่เปลี่ยนค่าสถานะก็มีได้ หากเปลี่ยนประสบการณ์หรือแสดงนิสัยของผู้เล่น
- ให้ผลสอดคล้องกับการกระทำและขนาดของเหตุการณ์ เช่น งานพิเศษเพิ่มเงินแต่กินเวลา การพักช่วยสุขภาพ การซื้อของลดเงิน อย่าให้ค่าสถานะเพิ่มเพียงเพราะตัวเลือกนั้นฟังดูดี
- เขียน `recap` ให้ทุก Choice ในเนื้อหาใหม่ แม้ Schema จะอนุญาตให้เว้นได้ Recap ต้องเล่า **สิ่งที่เกิดขึ้นหลังเลือก** ด้วยข้อเท็จจริงที่แน่นอนสำหรับทางเลือกนั้น ไม่อ้างผลจากการสุ่มหรือเหตุการณ์ภายหลังราวกับเกิดขึ้นแล้ว ผู้เล่นจะเห็น Recap ใน Event ถัดไป และ UI แสดงเพียงบรรทัดแรก
- ไม่ใช้ Emoji ใช้ชื่อมหาวิทยาลัยสมมติ **ม.บารพู** และตรวจชื่อคน สถานที่ ความสัมพันธ์ และเหตุการณ์ก่อนหน้าในเนื้อหาเดิมก่อนเพิ่มรายละเอียดใหม่

ตัวอย่างความสัมพันธ์ระหว่าง Choice, Effect และ Recap:

| Choice                       | Effect                    | Recap ที่สอดคล้อง                          |
| ---------------------------- | ------------------------- | ------------------------------------------ |
| รับงานพิเศษช่วงบ่าย          | `money +240`, `health -2` | ได้ค่าจ้าง แต่กลับถึงห้องด้วยความเหนื่อย   |
| เลื่อนซื้อของที่ยังไม่จำเป็น | `effects: []`             | ลบของออกจากตะกร้าและเก็บเงินที่มีไว้ใช้ต่อ |

Effect ที่ใช้ได้ใน Choice คือ `statDelta`, `setFlag`, `schedule` และ `chance` ตาม Schema ปัจจุบัน `schedule` เลื่อนการเปลี่ยนค่าสถานะหรือ Flag ไปยังช่วงเวลาหรือ Event ที่กำหนด ส่วน `chance` มีผลสำเร็จและล้มเหลวแยกกัน อย่าสร้าง Effect Type ใหม่เพื่อพาเรื่องไปฉากถัดไป เพราะ Story Flow ทำหน้าที่นั้นอยู่แล้ว เงินติดลบได้และเป็นเงินกู้อัตโนมัติ จึงควรพิจารณาผลของค่าใช้จ่ายด้วย

## ต่อ Story Flow

เนื้อหาอยู่ใน `public/content-v2/events.json` ส่วน Node และ Connection อยู่ใน `public/content-v2/flow.json` Event และ Choice ID ใหม่ใช้ภาษาอังกฤษ `snake_case` และต้องไม่ซ้ำ ID ของ Node และ edge ก็ต้องไม่ซ้ำและอ้างถึงปลายทางที่มีอยู่จริง ภาพ เพลง และเสียงอ้างด้วย Asset ID ที่มีใน `assets.json` เท่านั้น

- Event ปกติต้องมีทางออกอย่างน้อยหนึ่งเส้นต่อ Choice ID; หากทางเลือกหนึ่งแยกได้หลายเส้น ให้ใส่เงื่อนไขและทางสำรอง Event แบบ program, elective หรือ multi-select ใช้พอร์ต `next`
- `kind`, `year` และ `period` ของ Event เป็นป้ายกำกับสำหรับค้นหาใน BO **ไม่ได้กำหนดลำดับที่เล่นหรือเปลี่ยนเวลา** เส้นทางใน Flow กำหนด Event ถัดไป และ `Next Period` เป็นตัวเปลี่ยนเวลา
- Event ที่วางบน Flow board ไม่ได้ใช้ `event.conditions` เพื่อหยุดทางเข้า หากต้องการให้ Side Event เกิดเมื่อเข้าเงื่อนไข ให้ตรวจด้วย edge condition หรือ Condition Node และต่อทางข้ามไว้เมื่อไม่ผ่านเงื่อนไข `event.conditions` ใช้คัด Event ใน Random Pool
- Condition Node ต้องมีทั้ง `pass` และ `fail` ทุก Choice ต้องมีทางออก และทุกเส้นควรไปถึง Event, `Next Period` หรือ Ending ที่ตั้งใจไว้
- หากมีหลาย edge ออกจากพอร์ตเดียวกัน ระบบเลือก edge แรกตามลำดับในไฟล์ที่เงื่อนไขผ่าน จัด edge แบบมีเงื่อนไขก่อนทางสำรองที่ไม่มีเงื่อนไข
- Random Pool ใช้สำหรับเหตุการณ์ที่สุ่มเจอระหว่างทาง ไม่วาง Pool Event เป็น Event Node บนบอร์ด Random Node ต้องมีทั้ง `after` และ `fallback`

ตัวอย่างช่วงปิดเทอมแรก: `term_reflection` ต่อเข้าเหตุการณ์หลักของวันหยุด จากนั้น Condition Node ตรวจ `met_mali` เพื่อเลือกว่าจะพบ `break_message_from_mali` หรือข้ามไป `break_budget` ทั้งสองเส้นกลับมาที่ `break_budget` ก่อนดำเนินเรื่องต่อจนถึง `next_y1_break` แบบนี้ผู้เล่นทุกคนยังพบเหตุการณ์หลัก แต่คนที่เคยรู้จักมะลิจะมีฉากเพิ่มเติม

## ตรวจงานก่อนบันทึกหรือเผยแพร่

- อ่านบทสนทนา Choice และ Recap ของแต่ละทางร่วมกัน ตรวจว่า Recap บรรยายผลที่เกิดจริง และผลค่าสถานะไม่ขัดกับเรื่อง
- ตรวจเส้น `pass`/`fail`, ทางเลือกไม่มีผล, เงื่อนไขที่ผ่านและไม่ผ่าน, เส้นสุ่มและ fallback รวมถึงทางเข้าสู่ `Next Period` เพื่อไม่ให้เกิดทางตันหรือข้ามเหตุการณ์หลักโดยไม่ตั้งใจ
- ใช้ตัวตรวจของ BO และ Schema ร่วมกันเพื่อตรวจ ID ซ้ำ พอร์ตที่ขาด ลิงก์เสีย และ Asset ID ที่หาไม่พบ สำหรับเนื้อหาที่แก้ ให้รัน focused test ที่โหลดเนื้อหาจริง เช่น `pnpm exec vitest run src/content/v2/loader.test.ts`
- ก่อนเผยแพร่ ให้พิจารณา `contentVersion` และผลต่อเกมที่กำลังเล่นค้างอยู่ตามกติกา save ปัจจุบัน
